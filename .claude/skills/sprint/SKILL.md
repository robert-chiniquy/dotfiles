# Sprint

An item is one acceptance. A block establishes the next unproved connection in the project's completion criteria, or removes a demonstrated prerequisite. Pack the largest compatible bin of work that makes that delivery cheaper and fits one context window. A heavy item is its own block. Preview one prompt; on approval, execute it in this session. Do not ask the user to paste it.

## Common mistakes

- Maximizing the ready queue before choosing the capability to demonstrate.
- Treating a dated status claim, review verdict, or matching host outputs as semantic authority.
- Adding a helper while leaving the same fact independently decided elsewhere.
- Checking a successful value without the premises, identity, or context that justify it.
- Calling separate agent results an integrated delivery, or omitting fixtures from its commit.
- Inventing a more-reduced form, moving an expectation without required approval, or stopping all work for one blocked decision.
- Copying a project's language laws or phase sequence into this global skill.

## Identify

1. Read the sprint-ground document named by the project contract, its completion criteria, current design guidance, and newest audit/handoff corrections. If none is named, use the project's stated goal. Record the actual revision and relevant uncommitted work. Requirements govern; dated completion claims must be reconciled with current evidence.
2. Read the latest project review, including its reviewed revision and successor notices. Check whether findings still apply before correlating them with the tracker. Update existing items; file actionable gaps without duplicating repeated reviews. A review's interpretation needs source authority just as an implementation does.
3. Identify the next unproved connection required by those completion criteria. Name its real consumer, input, required outcome, and independently checkable evidence. For a prerequisite repair, name the blocked consumer and explain why that repair enables it. A source record, isolated primitive, or syntax check proves only its stated part of a larger execution path.
4. List bounded acceptances. Sentences of one task are one item; neighboring files are not a capability. Drop paused work, unchosen designs, and items whose required result is unstated. If a mechanism already exists, verify the missing contract or integration rather than propose another implementation. A green rerun alone is not new delivery.
5. Pack executable items around that capability, preferring work that shares settled contracts and makes the delivery cheaper. Isolate work whose complexity would compromise the block. Do not add unrelated work merely because it is available. A block need not complete an entire milestone to remove a demonstrated prerequisite.
6. Before asking what to do next, survey remaining authorized work. An unresolved decision blocks its dependent work; continue independent items. Do not ask the operator to perform the packing or reopen settled project facts.

## Factoring and verification

For a consequential runtime or contract change, state:

- The fact being decided and its authoritative source or host invariant.
- The representation and components that currently decide it, including fallbacks, caches, and native peers.
- Whether the change unifies a decision, preserves a necessary distinction, or changes representation without changing meaning. Name any independent decision it removes; shared final output alone does not establish unification.
- The successful example, the plausible wrong implementation it would also pass, and the nearest meaningful check that distinguishes them: residual, false, conflicting, differently scoped, or a host lifecycle case.

Use the project's own factoring principles to answer these questions. For example, when the project requires internalization, inspect whether a host-only condition or policy should use the existing theory representation. This skill does not supply language laws or mandate a new abstraction.

Derive expectations from the approved source contract or host invariant independently of the implementation. Reviewers must state that authority and consider counterevidence. Matching implementations can share an error. Unknown outcomes are not permission to copy current output into an oracle. New tests must distinguish behavior or invariants; do not add tests that merely mirror implementation or wording.

A test pinned at F1 is not permission to prevent justified further reduction to F2. Do not invent F2 or roll an improved implementation back merely to preserve F1. Establish the derivation and retained premises, then follow the project's expectation-change policy; where approval is required, leave the pin unchanged until approval and report its mismatch explicitly. Host agreement alone does not authorize repinning. Continue other executable work.

If native hosts differ, either bring them to the justified result or explicitly account for the temporary difference: its cause, the factoring that produces it, and why it is appropriate under the project contract. Distinguish a regression from an approved limitation or improvement. Do not weaken checks to conceal a regression.

## Questions and approval

Ask about a concrete unresolved decision when the survey finds no remaining item executable without it. Name the affected acceptance, evidence, and consequence of each supported interpretation. Use the project's current dependency model; do not impose a phase sequence from this skill. A language statement remains authoritative in the current phase.

Use the question tool as specified by `questioning-the-user`, one question at a time. If detail will not fit, write Markdown and open it. Do not invent a result as a choice or ask the user to operate the tracker. When the answers suffice, preview the prompt in that turn.

Approval of a preview authorizes execution of that block without a second confirmation. Honor existing authorization: “do the next sprint” identifies and executes the next block in that turn. Incorporate corrections that preserve the authorized scope; a materially changed scope needs a revised preview and approval.

## Prompt

Emit one fenced prompt containing:

- Repository path, tracker command, actual baseline, and relevant in-flight work.
- Target capability or prerequisite, its consumer, and each bounded acceptance.
- Applicable settled project facts, their sources, exclusions, and any concrete unresolved decision.
- The factoring decision and discriminating verification appropriate to the change.
- Owned files and integration responsibility when delegating; the project's test/build commands and required combined-tree checks.
- Continue every authorized, executable item until complete. Stop dependent work only for a named missing decision or authority; continue independent work. Do not ask to proceed.
- Commit only completed block work, including its required fixtures. Publish only within the operator's authorization; do not infer publication permission from sprint approval.

Before approval, name the block and its acceptances concisely, then show the prompt. Do not repeat the entire plan in several formats.

## Execute and integrate

Assign one integration owner when delegating. Parallel implementations share the agreed contract and fixtures; independent review checks their interpretation, including the possibility of a shared mistake. Source-layer work and separate host implementations may proceed together where their shared contracts are settled. Avoid simultaneous incompatible edits to a shared decision owner.

Run focused checks first, then the project's appropriate regression gates on the combined tree. Verify prerequisites before dependent operations. Preserve the operator's existing regression and expectation-approval rules. Check that all required inputs are included in the delivery; passing in a dirty checkout is not proof that the committed tree contains the tested program.

Record the exact tested revision or uncommitted diff and distinguish pre-existing failures from regressions. Verify the final commit contains the tested work and fixtures; if integration or concurrent edits change the tested code, rerun the affected checks. Separate agent completion messages do not close the combined acceptance.

If a required gate remains red on an unrelated pre-existing or decision-blocked case, identify that case and its baseline, follow the project's policy for committing independently completed work, and report the verification limit. Do not mark the gate or its dependent acceptance complete. A failure introduced by this block is a regression to repair, not an exception to classify as unrelated.

Commit completed work without including others' edits. A diagnosis with no file change has nothing to commit. Documentation is a deliverable when requested, but does not establish an implementation milestone.

## Reply

Report only this block, grouping results that share an outcome:

- What now works, with the actual input/program and result or failure.
- Why that result follows from the contract, what changed, and which distinction the counterexample verifies.
- What was executed on which tree, what was not checked and why, and any unresolved mismatch or regression.
- Which capability or prerequisite is now established, what it enables next, and why the block ended there.

For executed Occult evaluations, use the actual fixture, rendered term, host state, and each host's numeric cost. Cost is not the budget. Label host-only checks. Follow other projects' own evidence conventions. A file path or “costs differ” is not a result explanation.

Close only verified acceptances, not an item whose remaining clauses were skipped. Report progress in the project's completion criteria; do not substitute closed-item counts or invented percentages. If a necessary next decision remains after the work survey, ask that concrete question in the same reply.

Check for a review newer than the one used at dispatch. If present, state what tree it reviewed and reconcile relevant corrections with the tracker. Do not wait for a review to appear or create duplicate work from a repeated assessment of the same tree.

## Before finishing

- [ ] The block advanced a named capability or demonstrated prerequisite; its real consumer and next connection are explicit.
- [ ] Expectations came from the contract or host invariant; contrary cases were checked, and any required pin-change approval was preserved.
- [ ] Changed decisions have an explicit authority; host differences and remaining independent mechanisms are accounted for.
- [ ] The combined tree was verified, required fixtures are committed with the work, and unrelated edits remain untouched.
- [ ] The report states actual evidence, limits, goal progress, and the stopping reason; independent authorized work was not abandoned for one blocked decision.
